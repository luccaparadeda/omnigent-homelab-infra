# Current-stack research — 2026-10-26

> A subsequent comparison of alternatives recommends making OCI Resource
> Manager plus Ansible the steady-state path, with manual OCI creation plus
> Ansible for the first deployment. See
> [Provisioning alternatives and recommended operating model](research-iac-alternatives-2026-10-26.md).

## Recommendation

Use a deliberately small four-layer stack:

1. **OpenTofu 1.13.x + OCI provider 9.11.0** for optional Oracle resource lifecycle.
2. **cloud-init** only for the first boot user, SSH key, Python, and baseline hardening.
3. **Ansible Core 2.21.5** for the same guest configuration whether Oracle VMs were created by OpenTofu or by hand.
4. **Ubuntu autoinstall + Ansible** for the dedicated bare-metal home worker; **Packer 1.16.2 + QEMU plugin 1.1.7** remains optional for test/virtual workers.

Do not introduce Kubernetes, Crossplane, AWX, or a secrets operator at this scale. They would add a larger control plane than the workload. Docker Compose and systemd are enough for two small VPS nodes and two workers.

## Oracle free-tier fit

Oracle currently documents an Always Free Ampere A1 aggregate of 1,500 OCPU-hours and 9,000 GB-hours monthly, equivalent for a continuously running tenancy to **2 OCPUs and 12 GB RAM total**. The repository allocates:

- control plane: 1 OCPU / 8 GB
- Vault: 1 OCPU / 4 GB

Both use Ubuntu 24.04 ARM64 with 50 GB boot disks. The safety guard prevents a plan from exceeding 2 OCPUs or 12 GB. Oracle capacity is not guaranteed; `out of host capacity` requires another availability domain or waiting.

Oracle also currently lists software-protected KMS keys as free, the first 20 HSM-protected key versions as free, and 20 GB of combined Always Free Object Storage. This design uses a software-protected KMS key and requires explicit backup retention monitoring.

## Why Ansible is the center

The user can create Always Free instances in the OCI Console, then provide only private-overlay addresses in inventory. No OCI API key is required for that route. The same roles also work after OpenTofu creation and on a physical Linux home worker.

Ansible Vault is acceptable for short-lived bootstrap material, but it is not
the runtime credential system. Runtime MCP credentials belong in Omnigent's
credential store encrypted through Vault Transit. Native Codex and Claude
subscription logins and the Omnigent host identity remain device-local because
the process must authenticate somehow. The accepted design uses no paid model
API keys, keeps subscription sessions in a password-unlocked OS keyring, and
removes rootful Docker access from the worker user.

## MCP finding

Omnigent 0.19 introduced a server MCP registry and gateway. Managed accounts can be connected in Settings and their tools selected for local hosts or sandboxes through the server gateway with policy checks. That matches the requested model: reusable connections can exist centrally without permanently binding project A to credential A. Access policy can be tightened later without changing the topology.

The published 0.19.1 server image supports ARM64 but does not contain the optional `hvac` library required by the Vault credential cipher. The repository therefore builds a derived server image from the immutable official digest and installs only `hvac==2.4.0`, verified against its PyPI wheel hash.

## Security decisions

- The public subnet exists for outbound connectivity and bootstrap, not public applications.
- No ingress is created by default. Temporary SSH forbids `0.0.0.0/0`.
- Omnigent and Vault bind to Tailscale addresses after enrollment.
- Vault uses its OCI instance principal for KMS auto-unseal; no Oracle user API key is stored on the node.
- Losing the KMS auto-unseal key can make restored Vault data unusable, so the key has `prevent_destroy` and needs its own governance.
- Logical PostgreSQL backups and application-state archives are separately streamed into `age` encryption before upload with an instance principal.
